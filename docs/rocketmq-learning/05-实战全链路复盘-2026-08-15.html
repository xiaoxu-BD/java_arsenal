实验一 · "异步发送"的真相

原代码注释写着"异步不阻塞"，实际 convertAndSend 是同步阻塞。改造为真 asyncSend + SendCallback 后，接口耗时从 204ms → 6.8ms。

2026-08-15T10:09:38.875 INFO [http-nio-18082-exec-1] ProduceRockerMQDEM : [同步发送] 阻塞 77ms 拿到 broker 确认才返回 2026-08-15T10:09:38.981 INFO [http-nio-18082-exec-2] ProduceRockerMQDEM : [异步发送] 发起 asyncSend，主流程不等待确认 2026-08-15T10:09:38.995 INFO [NettyClientPublicExecutor_5] ProduceRockerMQDEM : [异步回调-成功] msgId=2408820C…EA90001 queue=3 status=SEND_OK ← +14ms，另一个线程！ 2026-08-15T10:09:41.444 INFO [ConsumeMessageThread_…_1] ConsumerRocketMQDEML : [消费者] 收到消息: hello rocketmq ← 2.4s 后
✅ 三个证据
① 接口 6.8ms 返回，确认 14ms 后由回调线程送达（业务代码别指望 ThreadLocal 传过去）； ② 回调拿到完整回执：msgId / queue=3（轮询落点）/ SEND_OK；
③ 两条消息被 ConsumeMessageThread_1/_2 并发消费——消费线程池亲眼所见。
⚠️ 反直觉数字
发送确认只花 14ms，消费却在 2.4s 后（消费组刚启动，rebalance + 首拉）。
发送段和消费段是两本独立的账——"MQ 延迟高"要先分清是哪一段。

实验二 · 三 ID 同框

producer 用 MessageBuilder.setHeader(RocketMQHeaders.KEYS, …) 打业务键， consumer 换 RocketMQListener<MessageExt>，三个标识符一次看全。

标识符实测值（同一条消息）身份 & 用途
UNIQ_KEY 2408820C9009BF60…5E9C0000 客户端出生证：前缀=producer 进程指纹（同进程全一样），末 4 位=进程内计数器，四条消息 0000→0003 肉眼可数
offsetMsgId C0A8C88000002A9F0000FEF7 broker 门牌号：C0A8C880 十六进制解码 = 192.168.200.128（你的 broker），后 8 字节 = CommitLog 物理偏移 65271，四条严格递增——所有消息混存顺序追加的铁证
Keys ORDER-1001 / ORDER-1002 你设置的业务标签：写进 IndexFile，控制台"按 Key 查询"一次捞出该业务实体全部消息；幂等去重键必须用它
为什么幂等别用 msgId
重试/死信是新的物理消息（offsetMsgId 会变），而业务键跟着消息体走、永远是那个订单号。 排障口诀：物理身份认 offsetMsgId，业务身份认 keys，血缘认 ORIGIN_MESSAGE_ID（06 节实测）。

悬案一 · "发了 4 条，消费 40+ 还一直涨"

侦破手段：不进虚拟机，直连 dashboard REST API（192.168.200.128:8080）取证。

证据链 全部实测

① topic 级对账
rocket-service-exm 四个 queue 共 9 条（1+3+2+3），最后写入 10:39——与真实发送完全吻合，消息清白
② 重试/死信排查
8 个 %RETRY% topic 24h 窗口全空；%DLQ% 一个都不存在（惰性创建，没消息死过）→ 排除重试循环
③ 集群口径
集群页数字是整台 broker 的账（含你虚拟机里 chain/order/pay 等其他项目 + 系统队列）；多项目共享一台 broker
④ 受控实验 · 观察者效应
浏览一次消息页（拉回 9 条）→ 消费计数精确 +9；再刷 → 再 +9。 331 → 340 → 349。TOOLS_CONSUMER（V5_3_3，docker 网关 172.18.0.1 出生）就是 dashboard 自己的查询组
⑤ 数字冻结
10:47 与 10:57 两次采样 32/331 纹丝不动——"一直涨"跟着浏览和测试活动走，停手即停涨
口径沉淀
集群页 Consume Count = 出手次数（每次拉走都 +1：多消费组各算、dashboard 浏览也算、历史消息翻出来也算、重投也算）。 判断业务健康永远下钻到 topic 的 maxOffset 和 消费组的 Diff（积压）——你的 Diff 全程为 0。
附：优雅停机的意义
强杀进程会"消费了但位点没提交"，下一个实例重拉一遍、消费数重计——这就是生产要 graceful shutdown 的原因（先下线消费、提交完位点再退出）。

真实事故 · 一条手抖消息的 3 小时循环

上午手动在 dashboard 注入消息（body 缺 sendTimestamp 字段）→ Long.parseLong(null) 炮弹 → 确定性错误在重试循环里空烧。

15:18:29.425 WARN [onsumer-group_4] DefaultRocketMQListenerContainer : consume message failed. messageId:AC12000400012FF4ACD048EE98C50010 topic:rocket-mail-topic reconsumeTimes:7 java.lang.NumberFormatException: Cannot parse null string at java.base/java.lang.Long.parseLong(Long.java:674) at org.xiaoxu.consumer.SendMailLogicConsumer.onMessage(SendMailLogicConsumer.java:36) ← parseLong(message.get("sendTimestamp"))

broker 取证 %RETRY%email-consumer-group

  • 两条一模一样的毒消息：出生 11:51:36 / 11:51:39（间隔 2.8s，提交了两次），bodyCRC 完全相同
  • 出生地 172.18.0.1（docker 网关 → dashboard 注入的指纹）
  • 均烧到 第 7 次重投，DELAY=9（5 分钟/跳），后续 6m、7m…最長 2h，到 16 次约需 4~5 小时

修复（方案 B：防御式消费）15:31 循环熄火

修前
long startTime = Long.parseLong(sendTimestamp); // sendTimestamp == null → 必炸 // 且第51行还有第二颗雷： // 发送成功后打日志再 parseLong 一次
修后
// email 缺失 → WARN + ACK 跳过 // 时间戳防御解析，失败返回 -1 long startTime = parseSafely(sendTimestamp); long delay = startTime > 0 ? recv - startTime : -1;
15:31:31.283 INFO [onsumer-group_1] SendMailLogicConsumer : [链路监控] 排队耗时:-1ms, 邮件发送耗时:1727ms（无 sendTimestamp，跳过链路统计） 15:31:31.296 INFO [onsumer-group_2] SendMailLogicConsumer : [链路监控] 排队耗时:-1ms, 邮件发送耗时:1740ms // 下一次重投即被成功消费 → ACK → 循环自然终止，真实邮件送达
核心教训
重试只能治瞬时故障（网络抖、下游超时），治不了确定性错误——缺字段的消息重试 16 次也不会长出字段。 消费端分层：脏数据防御性解析、快速失败；值得重试的才放行进 %RETRY%；重试终会成功的场景业务可能已做了一半 → 幂等是最后一道闸。 本案账单：2 条 × 8 次失败 + 2 次成功 = 18 次投递全部计入集群消费数。
08

模型修正 · 复述里的三处精确化

对"投递必达 → 失败进重试 → 16 次进死信 → 专人监听"这段复述的修正（原始方向全对）：

复述精确版
"超过 16 次转死信"16 只是并发模式默认值（顺序模式默认 Integer.MAX_VALUE，原地重试不进死信）。demo 组配 maxReconsumeTimes=1 → 实测 2 次即入死信。这是业务决策不是法律
"一直重试"指数退避：10s→30s→1m→…→2h，走完默认全程约 4~5 小时。生产上别等死信，%RETRY% 堆积本身就是告警信号
"无论如何都会发过来"严格说是 At Least Once：不但一定来，重平衡/崩溃时还可能来不止一次 → 幂等是必修不是选修。另：广播模式没有重试和死信，失败即过
"写一个消费者监听死信"对，但两个要点：必须用新的 consumerGroup（同组会打乱订阅关系）；%DLQ% 按消费组聚合（不按 topic），组内所有 topic 的死信汇于一处，接盘逻辑靠 RETRY_TOPIC 属性认祖归宗

结论二 · broker 的"今天"按 UTC 日切 北京时间早 8 点才是它的新一天

"今日生产 48"的真相
dashboard 所有时间戳带 Z 后缀（11:35:45Z = 19:35 CST）——broker JVM 跑在 UTC， 它的"Today"计数器在 UTC 0 点 = 北京时间早 8 点才翻转。于是早上看到的"今日生产 48"里装着 昨天早 8 点以来的全部写入（含昨天下午的毒消息实验和邮件风暴）。
生产含义：用这个口径做容量日报 / 监控告警，数字会歪 8 小时——先校 broker 时区。

结论三 · 跨 binder 失败的连锁反应 下游的病，上游的重试队列吃药

06:37
cross-msg-1 进入 notifyProcess 函数（RocketMQ 进 → RabbitMQ 出）
出站撞墙
RabbitMQ 认证 401 → 函数抛异常 → RocketMQ 判定消费失败 → %RETRY%stream-notify-group
9 跳 × 40 分钟
每跳重投都再撞认证墙，DELAY 从 3 档爬到 11 档；期间 broker 多出 9 个重试副本（见结论一）
凭证修复
第 10 跳成功：函数完成 RocketMQ→RabbitMQ 转发，循环熄火，无死信——重试机制扛住了配置故障，消息自动续命
架构推论
Stream 屏蔽了收发 API，但没有屏蔽失败传播：下游 MQ 的故障会以"消费失败"的身份污染上游 MQ 的重试队列 （还会把副本灌进上游的生产计数）。跨 binder 链路要把出站失败的兜底（errorChannel / 重试上限 / 降级）当作一等公民设计。
增补后的对账方法论（第 3 版）
① 先问口径：这个数统计什么？时间窗口从哪到哪（时区）？
② 再拆构成：真实发送 + 重试副本 + 死信副本 + 观察者（浏览）各自贡献多少；
③ 下钻验证：逐 topic 数消息求和，与集群计数对账——数字不会说谎，但口径会。
