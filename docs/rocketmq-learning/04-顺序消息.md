# RocketMQ 学习笔记 · 第 4 课：顺序消息

> 前置要求：理解 Queue / Offset / 消费组（第 0、1 课）。
> 这是面试高频、也最容易在生产翻车的一课。

## 0. 阶段 2/3 自检（先答再往下看）

1. **为什么 RocketMQ 天然不保证全局顺序？**
   一个 Topic 默认 4 个 Queue，消息按轮询/随机/Key 哈希分散到各队列，
   消费端又是多线程并行消费——不同队列之间没有先后关系。

2. **一个消费组的消费并行度由什么决定？**
   由 Queue 数量和组内实例/线程数共同决定：Queue 是并行上限，
   多出来的消费者实例会空闲；单实例内多线程也并行消费不同队列。

3. **消费失败时 Offset 为什么不前进？**
   因为要"至少一次投递"：失败不提交 Offset，消息下次还会被投递，
   重复消费靠业务幂等兜底。

答不上来的点，回看第 0、1 课笔记。

## 1. 什么业务需要顺序消息

典型场景：**同一个订单的状态流转**。

```text
订单A：创建(1) → 支付(2) → 发货(3) → 完成(4)
```

如果消息乱序，可能出现"先处理发货、再处理创建"，业务直接错乱。
注意关键词是"**同一个订单**"——不同订单之间无所谓顺序，可以并行。

所以 RocketMQ 做的是**局部顺序（分区顺序）**：

- 全局顺序：整个 Topic 只有一个队列在消费，吞吐极低，几乎不用；
- 局部顺序：按业务 Key（orderId）把消息固定分到同一个队列，队列内有序。

## 2. 发送端：让同一个 Key 永远进同一个队列

默认发送是"轮询选队列"，同一订单的消息会散到不同队列 → 乱序。
解决办法：自定义队列选择器 `MessageQueueSelector`，按 Key 哈希选队列。

原生 API 示意（看懂即可）：

```java
DefaultMQProducer producer = new DefaultMQProducer("order-producer");
producer.start();

Message msg = new Message("order-status-topic", body);
producer.send(msg, new MessageQueueSelector() {
    @Override
    public MessageQueue select(List<MessageQueue> mqs, Message msg, Object arg) {
        // arg 传订单号；同一订单号永远哈希到同一个队列
        int index = Math.abs(arg.hashCode()) % mqs.size();
        return mqs.get(index);
    }
}, orderId);
```

Spring 框架对应一行：

```java
rocketMQTemplate.syncSendOrderly("order-status-topic:tag", msg, orderId);
```

`orderId` 就是 selector 的 `arg`，框架帮你按它选队列。

## 3. 消费端：队列内串行消费

光发送有序还不够，消费端也得"一个队列一个线程、按顺序处理"。

原生 API：注册 `MessageListenerOrderly`（而不是 `MessageListenerConcurrently`）。
Spring 注解方式：

```java
@RocketMQMessageListener(
    topic = "order-status-topic",
    consumerGroup = "order-status-group",
    consumeMode = ConsumeMode.ORDERLY   // 关键！默认是 CONCURRENTLY
)
public class OrderStatusConsumer implements RocketMQListener<OrderEvent> {
    // onMessage 同一队列严格串行调用
}
```

底层做了什么：

- 同一个队列内的消息，同一时刻只有一个消费线程在处理；
- Broker 端有 `RebalanceLockManager`（消费队列锁），防止 Rebalance 时
  两个实例同时消费同一个队列；
- 消费失败时**不会跳过**，而是把整个队列挂起，按延迟重试（延迟逐级递增），
  等这条处理成功才继续下一条。

## 4. 有序 vs 无序：失败重试语义的差别（重点）

| | 无序消费（CONCURRENTLY） | 有序消费（ORDERLY） |
| --- | --- | --- |
| 失败返回 | `RECONSUME_LATER` | `SUSPEND_CURRENT_QUEUE_A_MOMENT` |
| 后续消息 | 继续消费，失败消息进重试队列 | **整个队列暂停**，等重试成功 |
| 重试方式 | 交给 %RETRY% 队列，可与后续消息错开 | 当前队列定时重试，顺序不被打乱 |
| 重复风险 | 高，必须幂等 | 也有（重试），同样要幂等 |
| 吞吐 | 高，多队列多线程 | 低，单队列串行 |

## 5. 常见坑

1. **Topic 队列数不能随便改**：队列数变化会让相同 Key 哈希到不同队列，
   顺序被破坏。生产上 Topic 建好后队列数保持固定；
2. **消费者实例数不要超过队列数**：多出来的实例完全空闲，白占资源；
3. **一个队列卡住影响整条链路**：某条消息一直失败，它后面的所有消息
   都被堵住——要有死信/告警机制，避免队列永久挂死；
4. **顺序消息吞吐上限 = 单队列 TPS**：全局顺序更慢，能不用就不用；
5. **顺序消息也要幂等**：消费重试依然可能重复投递，去重逻辑不能省。

## 6. 和 Kafka 的对照（先记着，学 Kafka 时展开）

Kafka 里对应概念是 **Partition（分区）**：同 Key 的消息进同一 Partition，
Partition 内有序；RocketMQ 的 Queue ≈ Kafka 的 Partition。
两者都是"分区内有序、跨分区无序"，这是分布式 MQ 的通用设计。

## 7. 练习建议（第 2 课之后做）

在你的 `rocketmq-service` 里加一个订单状态流转 Demo：

1. 发 30 条消息：10 个订单各 3 条状态（CREATE → PAY → SHIP），
   用 `syncSendOrderly(topic, msg, orderId)`；
2. 消费端先用默认 `CONCURRENTLY` 收一次，打印每个订单的接收顺序，观察乱序；
3. 改成 `ConsumeMode.ORDERLY` 再收一次，对比每个订单是否严格按序；
4. 故意让某条消息抛异常，观察有序消费"整队列挂起重试"和
   无序消费"跳过继续"的差别。

**验证方法**：消费端用 `Map<orderId, List<status>>` 记录顺序，最后检查
每个订单的状态序列是否严格递增。
