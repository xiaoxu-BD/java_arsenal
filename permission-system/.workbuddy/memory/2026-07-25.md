# 2026-07-25

## BUG 根因确认：FulfillmentOrder 分页查询的 userId 隔离
- 疑问：FulfillmentOrderServiceImpl.pageQuery 分页是否应该用 userId 过滤？
- 结论：当前分页"已经"按当前登录用户隔离，但用的是 `applicant`（用户名字符串），不是 `userId`。
- 证据：
  - 实体 `FulfillmentOrder` 有 `userId`(Long, 注释"申请人用户ID") 字段（FulfillmentOrder.java:37-38）
  - Controller.list 强制 `query.setApplicant(authentication.getName())`（FulfillmentOrderController.java:48），Service 用 `wrapper.eq(applicant, ...)` 过滤（FulfillmentOrderServiceImpl.java:79-81）
  - create 只 set applicant/creator；FulfillmentOrderCreateDTO 与 MapStruct 均无 userId → `userId` 永远为 null（死字段）
- 风险：userId 全表 null 无法关联/统计；applicant 依赖用户名，改名或换登录体系会失效；隔离依赖调用方注入可绕过；getDetailById/deleteById/changeStatus 无归属校验（越权）。
- 决策：用户选择"暂不修改，仅确认根因"，后续排期修复。
- 修复方向（待定）：A) 改用 userId 隔离（需鉴权能提供 userId，当前仅 authentication.getName()）；B) 补写 userId 仍用 applicant 隔离；并把隔离逻辑下沉到 Service + 补全归属校验。
