# 企业级支付平台（Payment Platform）项目上下文

## 1. 项目定位

设计并实现一个企业级支付中心。

**目标：**

建设一个独立的支付能力平台，为多个业务系统提供统一支付服务。

**接入方可能包括：**

- 审批系统
- 报销系统
- 采购系统
- 电商系统
- 其他未来业务系统

**核心思想：**

业务系统不直接对接第三方支付平台。

**统一流程：**

```
业务系统
    |
    |
支付中心
    |
    |
支付宝 / 微信 / 银联 / 其他支付渠道
```

**支付中心负责：**

- 支付订单创建
- 支付渠道选择
- 支付请求
- 支付回调处理
- 状态维护
- 幂等处理
- 退款
- 对账
- 通知上下游系统

## 3. 已完成业务背景分析

### 为什么需要支付中心？

如果每个业务系统自己接支付：

例如：

- 审批系统 -> 支付宝
- 报销系统 -> 支付宝
- 采购系统 -> 支付宝

**会产生：**

1. 重复开发
2. 每个系统维护自己的支付逻辑
3. 回调处理方式不统一
4. 增加微信、银联等渠道成本高
5. 后期维护困难

所以抽象支付中心。

---

## 4. 支付中心核心流程

**当前确定主流程：**

```
业务系统发起支付请求
    ↓
支付中心接收请求
    ↓
参数校验
    ↓
创建支付订单
    ↓
调用支付渠道
    ↓
用户完成支付
    ↓
第三方支付平台异步回调
    ↓
支付中心验签
    ↓
更新支付订单状态
    ↓
发送 MQ 消息
    ↓
通知业务系统
    ↓
业务系统更新自己的业务状态
```

---

## 5. 创建支付订单流程

**业务系统调用：**

```
POST /payment/create
```

**请求包含：**

- `businessOrderNo`
- `businessType`
- `amount`
- `paymentChannel`
- `callbackUrl`

**支付中心处理：**

### 第一步：参数校验

例如：

- 金额不能为空
- 业务订单不能为空
- 支付渠道是否合法

### 第二步：幂等检查

防止：同一个业务请求重复创建支付单。

### 第三步：创建支付订单

状态：`WAIT_PAY`

### 第四步：调用第三方支付

---

## 6. 支付回调设计

**第三方支付回调不能直接相信。**

**必须处理：**

### 1. 验签

确认：

- 请求来源合法
- 参数没有被修改

例如：支付宝签名验证。

### 2. 金额校验

本地：`100元`

第三方：`100元`

必须一致。防止金额被篡改。

### 3. 幂等处理

原因：支付平台可能重复通知。

例如：

第一次：`WAIT_PAY -> PAID`

第二次：同一个通知再次到达。

**不能：**

- 重复更新
- 重复发送 MQ
- 重复执行业务

---

## 7. 状态机设计

**当前基础状态：**

```
CREATED
   ↓
WAIT_PAY
   ↓
PAID
```

**后续扩展：**

```
CREATED
WAIT_PAY
PAID
FAILED
CLOSED
REFUNDING
REFUNDED
```

**原则：** 状态必须符合业务规则。

例如：禁止 `PAID -> WAIT_PAY`

---

## 8. 支付渠道抽象设计

**不要：** 在业务代码里面写：

```java
if (channel == ALIPAY) {
    // ...
} else if (channel == WECHAT) {
    // ...
}
```

**应该抽象：**

```java
PaymentChannel
```

**接口：**

```java
pay()
queryOrder()
refund()
```

**实现：**

- `AlipayChannel`
- `WechatChannel`
- `UnionPayChannel`

**好处：**

未来增加支付渠道，只需要新增实现，核心流程无需修改。

---

## 9. 支付异常处理

**问题：** 支付宝已经扣钱，但是回调没有收到。

**结果：**

- 支付宝：成功
- 支付中心：`WAIT_PAY`

数据不一致。

**解决：** 主动查询。

**设计：** 统一接口 `PaymentChannel.queryOrder()`

例如：

- 支付宝：`AlipayChannel.queryOrder()`
- 微信：`WechatChannel.queryOrder()`

**定时任务：**

扫描 `WAIT_PAY` 订单 -> 调用渠道查询 -> 如果成功 -> 更新本地订单 -> 发送 MQ

## 11. 核心表设计

**第一张核心表：** `payment_order`

支付订单主表。

**职责：** 保存一笔支付完整生命周期。

包括：创建、支付、成功、失败、关闭、退款。

---

## 12. payment_order 与 businessOrderNo

**重点理解：** `businessOrderNo` 不是支付中心自己的订单号。

它代表：**业务系统订单编号。**

例如：

- 审批系统：`APPROVAL_001`
- 报销系统：`EXPENSE_001`

支付中心保存。

**作用：** 跨系统关联。

---

## 13. paymentOrderNo

支付中心自己的订单编号。

**区别：**

- 业务订单：`businessOrderNo`
- 支付订单：`paymentOrderNo`

例如：

- 业务订单：采购单 001
- 支付中心：`PAY202607200001`

一个业务订单可能产生多个支付订单。

---

## 14. 业务订单和支付订单关系

**不是一定一对一。可能：一对多。**

**场景：**

### 分批支付

- 业务：10000 元采购单
- 支付：5000 + 5000
- 产生：两个支付单

### 支付失败重新创建

- 第一次：支付失败
- 第二次：重新创建支付单

---

## 15. businessOrderNo + 状态问题

**讨论：** 是否需要 `businessOrderNo + status` 唯一索引。

**理解：** 不能简单根据字段设计。

**业务规则：**

同一个业务订单：不能同时存在多个有效待支付订单。

但是：历史关闭订单可以存在。

**所以：**

- 业务层：负责判断
- 数据库：负责基础保护

**原则：**

业务层控制业务规则，数据库保证数据一致性。

---

## 16. 幂等设计总结

两个地方需要考虑幂等。

### 创建支付订单

防止：重复创建支付订单。

例如：网络超时，调用方重试。

解决：`businessOrderNo` 判断。

### 支付回调

防止：重复支付通知。

解决：状态机 + 条件更新。

例如：

```sql
UPDATE payment_order
SET status = 'PAID'
WHERE payment_order_no = ?
  AND status = 'WAIT_PAY'
```

如果影响行数为 0，说明已经处理过。

---

## 17. 技术选择原则

不要为了展示技术而使用技术。

例如：分布式锁。不是所有地方都需要。

**支付回调幂等：**

优先考虑：数据库状态控制。

**原因：**

- 简单
- 可靠
- 容易维护

只有：多个资源竞争、复杂协调、高并发场景，再考虑：Redis 分布式锁。
